# P0.4: 故障注入实验执行手册

**实验目标**: 证明 FlowGap 能检测链路故障（带宽下降）

**预期结果**:
- 检测延迟: < 10 秒
- 召回率: > 80%
- 带宽 time series: 故障前后清晰对比

**所需时间**: 约 2 小时（1 轮训练 100 分钟 + 准备/分析 20 分钟）

**前置条件**:
- Ascend 910B 服务器 × 1（8 卡）
- root 权限（用于 tc 限流）
- 已安装 MindSpore + MindFormers
- 已训练 GBDT 模型（`models/gbdt_pass1.pkl` 或 `gbdt_pass2.pkl`）

---

## 一、实验原理

### 1.1 故障注入方法

**方案 D: memcpy 带宽竞争**（推荐，真实有效）

使用后台 Python 脚本持续执行大块 memcpy，占用 NPU H2D/D2H 链路带宽，造成与训练的真实竞争。

```bash
# 启动带宽竞争注入器（占用约 50% 带宽）
python scripts/inject_bandwidth_contention_v2.py \
  --interval-ms 10 --duration 180 --direction D2H

# Ctrl+C 或等到 duration 结束自动停止
```

**原理**:
- 基于 `ProbeExecutor`（已验证可工作）
- 每次执行 128 MB 的 `aclrtMemcpy` (D2H 或 H2D)
- 间隔 10ms → 每秒约 100 次 → 占用约 12.8 GB/s (约 60% 带宽)
- 与训练的 memcpy 形成真实的链路竞争

**参数调整**:
- `--interval-ms 5` → 重度拥塞 (~70% 占用)
- `--interval-ms 20` → 轻度拥塞 (~30% 占用)
- `--direction D2H` → 仅 D2H（推荐，因为训练主要是 D2H）
- `--direction BOTH` → H2D + D2H（更激进）

**优点**:
- ✅ **真实故障**: 链路确实被占用，训练和探针都会受影响
- ✅ **可观测**: 探针测到的低带宽是真实的，不是伪造的
- ✅ **可控**: 通过调整间隔控制拥塞程度
- ✅ **论文可信**: 审稿人认可的真实带宽竞争

---

### 1.2 备选方案（仅供参考）

~~**方案 A: tc 限流 HCCS**~~  
❌ **不可行**: HCCS 是片上互联，不走 Linux 网络栈，`tc` 无法限流。

~~**方案 B: tc 限流 nic6/nic7**~~  
❌ **不可行**: HCCL 通信走 HCCS 内部，不走主机网卡。

~~**方案 C: CPU/内存压力**~~  
❌ **不可行**: 不影响 NPU 间的 HCCS 带宽。

### 1.2 检测逻辑

FlowGap 通过周期性带宽探针测量链路吞吐:
- **正常**: 20.4 GB/s (中位数, 基于 Pass 2 数据)
- **故障**: < 14.3 GB/s (70% 阈值)

**连续 2 次低带宽** → 确认检测 → 记录时间戳

### Step 1: 启动训练 + eBPF tracer + 探针循环

#### Terminal 1: 启动训练和 eBPF tracer

```bash
cd /root/FlowGap-work/FlowGap-paper

rm -f data/collected/p0.4_raw.log logs/p0.4_probe.log

# 启动 eBPF tracer（后台）

  --min-size 1000 \
  --output /root/FlowGap-work/FlowGap-paper/data/collected/p0.4_raw.log \
  --window-ms 100 \
  > /root/FlowGap-work/FlowGap-paper/logs/p0.4_ebpf.log 2>&1 &
TRACER_PID=$!
echo "eBPF tracer PID: $TRACER_PID"

# 等待 3 秒让 tracer 附加 uprobes
sleep 3

# 启动训练（前台或 nohup）
cd /root/mindformers/scripts
# 清理上次输出
rm -rf /root/mindformers/output/*

# 启动训练（修改配置为 20 分钟测试，或使用完整 100 分钟）
# 方法 1: 前台运行（可以 Ctrl+C 停止）
bash run_distribute.sh \
  /root/mindformers/mindformers/hccl_8p_01234567_192.168.39.155.json \
  ../configs/glm/run_glm_6b_finetune.yaml \
  '[0,8]' finetune

# 方法 2: 后台运行（建议用 nohup）
# nohup bash run_distribute.sh ... > /root/FlowGap-work/FlowGap-paper/logs/p0.4_training.log 2>&1 &
```

#### Terminal 2: 启动探针循环（带时间戳）

```bash
cd /root/FlowGap-work/FlowGap-paper/code
source /root/anaconda3/etc/profile.d/conda.sh
conda activate mindspore_py37

# 等待 trace 文件出现
while [ ! -f ../data/collected/p0.4_raw.log ]; do sleep 1; done
echo "Trace file detected. Starting probe loop..."

# 启动探针循环（flowgap_predictive 策略，带时间戳）
PYTHONPATH=.:trace_parser python probe_scheduler/online_loop.py \
  --trace-log ../data/collected/p0.4_raw.log \
  --probe-policy flowgap_predictive \
  --predictor-model-path ../models/gbdt_pass1.pkl \
  --budget-per-sec 2 \
  --timestamp \
  | tee ../logs/p0.4_probe.log
```

**重要**: `--timestamp` 选项为每次探针输出添加时间戳，P0.4 分析脚本依赖它。

## 五、常见问题

### Q1: 找不到 HCCS 接口怎么办？

**方案 A**: 跳过 HCCS 限流，改用**模拟故障**:
- 修改 `probe_executor.py`，在特定时间窗口内人为返回低带宽值
- 在论文中标注为 synthetic fault injection

**方案 B**: 限流网卡接口（如 `eth0`），影响 D2H 流量:
```bash
sudo bash scripts/inject_hccs_fault.sh start eth0 5gbit
```

### Q2: 训练中断了怎么办？

**不影响 P0.4**。只要有:
1. 探针日志（`p0.4_probe.log`，包含时间戳）
2. 故障注入的时间范围（`fault_start`/`fault_end`）

就可以运行分析脚本。训练是否完成不影响故障检测评估。

### Q3: 检测延迟很长（> 30 秒）？

可能原因:
1. **探针频率太低**: 增加 `--budget-per-sec` 到 5
2. **间隙不够**: 训练太密集，没有足够的安全窗口放探针
3. **路径不匹配**: 被限流的链路恰好不是主要的 memcpy 路径

解决: 检查 `bandwidth_timeseries.csv`，看是否有足够的 BW 探针采样到故障路径。

### Q4: 召回率很低（< 50%）？

可能原因:
1. **阈值太严**: `--threshold 0.7` 太低，改为 `0.8`（基线 80%）
2. **限流不够**: 5 Gbps 还不够低，改为 `2gbit` 或 `1gbit`
3. **探针路径偏移**: BW 探针恰好没有选中被限流的路径

解决: 降低限流带宽，或增加探针预算。
