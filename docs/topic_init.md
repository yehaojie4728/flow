## 1. One-sentence problem statement

How can we learn burst-gap patterns from Ascend intra-host memcpy traffic and predict safe probing windows to reduce probe interference to AI workloads?

---

## 2. Non-goals

FlowGap is NOT:

- a complete root-cause diagnosis system;
- a complete physical-link reconstruction system;
- a universal accelerator monitoring framework;
- a deep-learning traffic generation model;
- a paper that claims all Ascend workloads always have predictable gaps;
- an LSTM/Transformer-first approach;
- a full multi-node distributed tracing platform.

FlowGap IS:

- a probing opportunity inference layer for low-interference active probing.

---

## 3. Three contributions

1. **Safe-window prediction problem definition.**
   Define probing opportunity inference for Ascend memcpy traffic. Model path/link safety as multi-horizon survival probability.

2. **FlowGap Predictor and Scheduler.**
   Use eBPF event streams, probe-aware intervalization, async conservative/estimated timelines, and confidence calibration.
   Schedule probes only when predicted gap lower bound and confidence exceed thresholds.
   Support downgrade, cancellation, and failure-aware probing.

3. **Ascend 910A/910B evaluation.**
   Evaluate prediction accuracy, representation ablation, scheduling effectiveness, workload interference, detection utility, robustness, and system overhead.

## 4. SoCC cloud systems positioning

FlowGap is positioned as:

> a cloud / AI-infrastructure monitoring and active probing system that reduces measurement-induced interference in accelerator servers.

Broader cloud-systems relevance:

- AI training/serving clusters increasingly depend on accelerator servers;

- FlowGap reduces measurement-induced interference through safe-window prediction;

Avoid positioning as:

SoCC topic fit: Distributed systems, datacenter architectures, networking/communication, OS and system support, resource management/scheduling, ML for clouds, systems for ML training/serving, tracing and monitoring, fault tolerance/reliability.

## 6. Biggest rejection risks

1. **No real Ascend traces.** Without real trace data, Figure 1 (motivation) and all experiments are unsupported. This is a fatal blocker.

2. **Weak differentiation from Hostping/HostDiag.** Reviewer may ask: "Is this just HostDiag with a better scheduler?" Must clearly differentiate: FlowGap predicts *when* to probe; HostDiag decides *what* to diagnose after probing.

3. **Insufficient evaluation breadth.** SoCC expects systems evaluation spanning prediction accuracy, scheduling, interference, detection utility, robustness, and overhead. Each RQ must have supporting experiments and figures.

4. **Overclaiming.** Must not claim that FlowGap "eliminates" interference, "guarantees" diagnosis accuracy, or "works for all Ascend workloads." Claims must be calibrated to evidence.

5. **Missing baselines.** Must include: no probing, fixed, random, threshold, EWMA-only, survival-no-calib, fixed-window, oracle. Missing baselines weaken the evaluation.

6. **Anonymity violation.** Accidental author/institution reveal or public project name in the anonymous submission would cause desk reject.

7. **SoCC format violations.** Wrong template, page limit exceeded, wrong font, modified margins, PDF > 10MB.

8. **Simulation misrepresented as real measurement.** Must clearly label synthetic work and replay/simulation, never pass them as real Ascend measurements.
