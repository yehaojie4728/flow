# P0.4 实验分析报告：召回率不足的原因与参数调整建议

## 一、训练 memcpy 特性分析

基于 `p0.4_raw.log` 的统计（训练进程 PID 3608616-3609166）：

### 1.1 memcpy 大小分布
```
总记录数: 169,411（排除探针和注入器）
大小分布（按频次排序）:
  78,437 次 × 0.02 MB  (46.3%)
  34,870 次 × 0.01 MB  (20.6%)
  14,159 次 × 32.00 MB (8.4%)
  13,888 次 × 16.00 MB (8.2%)
   7,077 次 × 24.00 MB (4.2%)
   7,076 次 × 8.00 MB  (4.2%)
   6,944 次 × 4.00 MB  (4.1%)
   6,944 次 × 12.00 MB (4.1%)
```

**关键特征**：
- **67% 的 memcpy 是小块传输（< 0.1 MB）**，这些是训练参数同步、小梯度传输
- **33% 是大块传输（4-32 MB）**，这些是权重更新、激活值传输
- 训练的带宽需求是**突发性**的，并非持续高带宽

### 1.2 基线带宽特性
```
基线期间（注入前）:
  median = 0.79 GB/s
  mean   = 3.76 GB/s
  max    = 23.21 GB/s
```

**关键发现**：
- 训练的**中位数带宽只有 0.79 GB/s**（远低于理论 NPU-Host 带宽 ~25 GB/s）
- 这说明训练本身并非持续占满带宽，而是**间歇性传输 + 大量空闲**
- 峰值带宽可达 23 GB/s，说明硬件能力充足

## 二、故障注入效果分析

### 2.1 当前注入参数
| 注入阶段 | interval | 预期占用 | 实际效果 |
|---------|---------|---------|---------|
| 第1次（轻度） | 20ms | ~30% | 召回率 24.4% |
| 第2次（重度） | 5ms  | ~70% | 召回率 16.6% |

### 2.2 问题诊断

**召回率低于 80% 的根本原因**：

1. **训练带宽需求本身就低**
   - 基线中位数 0.79 GB/s，探针测量的"正常带宽"约 17-20 GB/s
   - 探针测的是**硬件可用带宽**（128MB 连续传输），而训练用的是**应用层带宽**（小块、间歇）
   - 故障注入占用了硬件带宽，但**训练本身就不需要那么多带宽**，所以影响有限

2. **注入强度与训练需求不匹配**
   - 注入器：128MB × 每 5-20ms = 6.4-25.6 GB/s 持续占用
   - 训练：0.01-32MB × 间歇性 = 0.79 GB/s 中位数需求
   - 当训练不需要大量传输时（67% 时间），故障注入的影响**被探针观测不到**

3. **探针的采样频率不足**
   - budget = 2 probes/s，每次探针耗时 ~7ms
   - 故障持续 5 分钟，理论最多 600 次探针，实际只有 903 次（全程）
   - 如果故障期间训练恰好在计算阶段（不传输），探针可能测不出异常

## 三、参数调整建议

### 3.1 提高故障注入强度（更激进的竞争）

**当前问题**：注入器和训练**错峰**了——注入器持续占用，训练间歇传输。

**建议**：
1. **降低 interval 到 1-2ms**（极限竞争）
   ```bash
   python scripts/inject_bandwidth_contention_v2.py \
       --interval-ms 1 --duration 300 --direction BOTH
   ```
   - 预期占用：~90% 带宽
   - 效果：即使训练需求低，也会因为竞争导致延迟增加

2. **同时注入 H2D + D2H**（`--direction BOTH`）
   - 训练是双向的（H2D 发参数，D2H 收梯度）
   - 双向注入更能覆盖训练的传输阶段

3. **增加注入持续时间到 10 分钟**
   - 当前 5 分钟可能只覆盖 1-2 个训练 iteration
   - 延长到 10 分钟，提高"撞上"训练传输阶段的概率

### 3.2 提高探针采样频率

**当前问题**：2 probes/s 太稀疏，故障期间可能只有 10-20 次探针。

**建议**：
1. **提高 budget 到 5-10 probes/s**
   ```bash
   --budget-per-sec 10
   ```
   - 5 分钟故障期间：10 × 300 = 3000 次探针
   - 更密集采样，减少"漏检"

2. **降低探针类型的开销**
   - 当前用 BW 探针（128MB，~7ms）
   - 可以混合使用 LAT 探针（4KB，~0.03ms），提高采样频率

### 3.3 调整故障检测阈值

**当前问题**：阈值 0.7-0.8（基线 × 70-80%）可能过于保守。

**建议**：
1. **基于训练实际需求设定阈值**
   - 训练中位数需求 0.79 GB/s
   - 探针基线 17.6 GB/s
   - 阈值应该是：**当探针带宽下降到接近训练需求时**才算异常
   - 建议阈值：< 5 GB/s（而非 < 14 GB/s）

2. **或者改用"延迟增加"作为指标**
   - 带宽下降不明显，但延迟可能增加 2-5 倍
   - 用 LAT 探针监测延迟，阈值设为基线 × 2

## 四、推荐实验方案

### 方案 A：极限竞争（验证故障可检测性）
```bash
# 故障注入参数
--interval-ms 1
--duration 600  # 10 分钟
--direction BOTH

# 探针参数
--budget-per-sec 10

# 检测阈值
--threshold 0.3  # 基线 × 30%，即 < 5.3 GB/s
```

**预期效果**：
- 召回率 > 80%（因为极限竞争，训练必然受影响）
- 检测延迟 < 10 秒（密集采样）

### 方案 B：真实场景（模拟实际故障）
```bash
# 故障注入参数
--interval-ms 3
--duration 600
--direction D2H  # 只注入训练主要方向

# 探针参数
--budget-per-sec 5

# 检测阈值（自适应）
根据基线动态计算：
  if 探针_median < 训练_median × 3:
      报警
```

**预期效果**：
- 召回率 60-70%（更真实，但可能仍低于 80%）
- 检测延迟 < 15 秒

## 六、结论

**回答你的问题**：

1. **是否因为注入力度不够？** — **是的**。训练本身带宽需求就低（0.79 GB/s），当前注入（6-25 GB/s）虽然占用了硬件带宽，但与训练的间歇性传输"错峰"了，导致探针检测不到明显异常。

2. **应该调整哪些参数？**
   - **interval-ms: 20/5 → 1-2**（极限竞争，避免错峰）
   - **direction: D2H → BOTH**（覆盖双向传输）
   - **duration: 300 → 600**（延长覆盖时间）
   - **budget-per-sec: 2 → 10**（提高采样密度）
   - **threshold: 0.7-0.8 → 0.3**（根据训练实际需求调整）
